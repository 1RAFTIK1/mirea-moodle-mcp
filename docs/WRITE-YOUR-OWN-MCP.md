## 0. Когда MCP вообще нужен

MCP нужен, когда модель должна **действовать или читать данные в системе, к которой у неё нет доступа**: твой Moodle, база, Jira, локальные файлы, домашний роутер. Сервер — это адаптер: «вот что можно сделать, вот аргументы, вот результат».

MCP не нужен, если хватит один раз вставить текст в чат, или если задача — «сгенерируй код» без обращения к внешней системе.

Три примитива протокола:

| примитив | кто инициирует | пример |
|---|---|---|
| **tools** | модель | `deadlines(days=7)`, `submit_assignment(...)` |
| **resources** | приложение/пользователь | файл лекции как вложение контекста |
| **prompts** | пользователь | шаблон «/разбери задание» |

В 90 % случаев достаточно tools. Этот проект использует только их.

## 1. Минимальный сервер за 80 строк

Полный рабочий код: [`examples/minimal-mcp/main.go`](../examples/minimal-mcp/main.go). Инструмент `shout` переводит текст в верхний регистр.

Скелет:

```go
sc := bufio.NewScanner(os.Stdin)
for sc.Scan() {                                   // 1 строка = 1 JSON-RPC сообщение
	var q req
	if json.Unmarshal(sc.Bytes(), &q) != nil || len(q.ID) == 0 {
		continue                                  // notification: отвечать нельзя
	}
	switch q.Method {
	case "initialize":  reply(q.ID, {protocolVersion, capabilities:{tools:{}}, serverInfo})
	case "ping":        reply(q.ID, {})
	case "tools/list":  reply(q.ID, {tools: [...]})
	case "tools/call":  reply(q.ID, {content:[{type:"text", text:"..."}], isError:false})
	default:            fail(q.ID, -32601, "method not found")
	}
}
```

Четыре метода — и это полноценный MCP-сервер. Всё остальное — удобства.

Описание инструмента — то, что **читает модель**:

```go
{
	"name":        "shout",
	"description": "Переводит текст в верхний регистр. Используй, когда пользователь просит «прокричать» фразу.",
	"inputSchema": {                       // JSON Schema — модель по ней строит аргументы
		"type": "object",
		"properties": {"text": {"type": "string", "description": "что прокричать"}},
		"required": ["text"],
	},
}
```

Ответ на `tools/call`:

```json
{"content":[{"type":"text","text":"ПРИВЕТ!!!"}],"isError":false}
```

`content` — массив блоков (`text`, `image`, `resource`…). Для данных почти всегда хватает одного текстового блока с JSON внутри.

## 2. Как проверить без Claude

### Руками через pipe

```sh
cd examples/minimal-mcp && go build -o mini .
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
  '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"shout","arguments":{"text":"привет"}}}' \
| ./mini
```

Ожидаемый вывод: три строки-ответа с `id` 1, 2, 3 (на notification ответа нет).

### MCP Inspector

Официальный отладчик с веб-интерфейсом: список инструментов, форма аргументов, лог сообщений.

```sh
npx @modelcontextprotocol/inspector ./mini
```

### Тесты на Go

Сервер — функция `serve(io.Reader, io.Writer)`, поэтому тестируется без процессов:

```go
func TestShout(t *testing.T) {
	in := strings.NewReader(`{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"shout","arguments":{"text":"a"}}}` + "\n")
	var out bytes.Buffer
	newServer(tools()).serve(in, &out)
	if !strings.Contains(out.String(), `"A!!!"`) { t.Fatal(out.String()) }
}
```

> **Хорошо:** проверил руками, работает. **Отлично:** `serve` принимает `io.Reader/io.Writer` — протокол покрыт unit-тестами, а парсеры HTML/ответов API — тестами на сохранённых фикстурах (`testdata/*.html`, `*.json`).

## 3. Подключить к Claude Desktop

Конфиг:

- macOS: `~/Library/Application Support/Claude/claude_desktop_config.json`
- Windows: `%APPDATA%\Claude\claude_desktop_config.json`

```json
{
  "mcpServers": {
    "mini": {
      "command": "/абсолютный/путь/к/mini",
      "args": [],
      "env": { "SOME_TOKEN": "…" }
    }
  }
}
```

Полностью перезапустить Claude Desktop (Quit). Если сервер не появился — смотреть логи:

- macOS: `~/Library/Logs/Claude/mcp-server-mini.log` и `mcp.log`
- Windows: `%APPDATA%\Claude\logs\`

Типичные причины: относительный путь в `command`; бинарник печатает что-то в stdout до ответа на `initialize`; падение на старте (видно в логе как stderr).

## 4. Проектирование инструментов — главное

Протокол — это 10 % работы. 90 % — чтобы **модель правильно выбирала и вызывала** инструменты.

### Гранулярность: по задачам пользователя, не по эндпоинтам API

Плохо: `get_course_contents`, `get_module`, `get_assign`, `get_submission_status`, `get_file_info` — модель должна сама собрать цепочку из пяти вызовов.
Хорошо: `get_activity(url)` — один вызов возвращает всё, что нужно для ответа «что задано и что я уже сдал».

Правило: *сколько вызовов нужно, чтобы ответить на типичный вопрос?* Цель — 1–3.

### Описание = промпт

```text
✗ "Get activity."
✓ "Открыть элемент курса по url (из course_contents/deadlines). assign: текст задания, сроки,
   файлы задания, статус моей сдачи; resource: ссылка на файл; folder: список файлов…"
```

В описании: **что** делает, **откуда брать аргументы** («url из course_contents»), **что вернёт**, **когда нельзя** вызывать без подтверждения.

### Аргументы

- Идентификаторы — те, что модель уже видела в ответах других инструментов (`url`, `cmid`), а не внутренние, которые ей негде взять.
- Разумные значения по умолчанию (`days=30`) — меньше вопросов пользователю.
- `enum` для фиксированных вариантов (`filter: inprogress|all|past|future`).
- Пути к файлам — абсолютные, с поддержкой `~/`.

### Ответы

- Компактный JSON с понятными ключами (`due`, `overdue`, `course`), время в часовом поясе пользователя и в читаемом виде.
- Выкинуть шум (служебные ID, HTML-разметку, пустые поля) — это токены и внимание модели.
- Ограничить размер (`max_chars`), не отдавать мегабайты.
- Давать «следующий шаг»: `url` у каждого дедлайна → модель сразу вызовет `get_activity`.

### Изменяющие действия

- Отдельный инструмент, `annotations: {"destructiveHint": true}`.
- Безопасный режим по умолчанию (черновик), необратимое — явным флагом (`finalize=true`).
- `dry_run` — проверить всё, кроме последнего шага.
- В `instructions` сервера: «перед finalize спроси пользователя».
- После действия — вернуть новое состояние (статус задания), чтобы модель могла убедиться, что всё получилось.

> **Хорошо:** инструменты работают. **Отлично:** по одному вопросу пользователя модель делает 1–2 вызова, ни разу не спрашивает «какой у курса id», не может случайно сделать необратимое действие, а ошибки говорят, что делать дальше.

## 5. Ошибки, логи, конкурентность

**Два уровня ошибок:**

| ситуация | как вернуть |
|---|---|
| неизвестный метод, битый JSON, неизвестный tool | JSON-RPC `error` (`-32601`, `-32602`, `-32700`) |
| инструмент не смог выполнить работу | `result` с `isError: true` и **человеческим** текстом |

Текст ошибки инструмента читает модель и пересказывает пользователю. Поэтому не `401 Unauthorized`, а «сессия истекла: войди в браузере и выполни `… cookie <значение>`».

**Логи — только в stderr.** Один `fmt.Println` в stdout — и клиент получит невалидное сообщение.

**Конкурентность.** Клиент может прислать несколько `tools/call`, не дожидаясь ответов. Обрабатывай каждый запрос в горутине, пиши в stdout под мьютексом, на EOF дождись всех (`sync.WaitGroup`). Иначе быстрый процесс-выход потеряет ответы — именно на этом споткнулась первая версия этого сервера.

**Паники.** `recover()` вокруг вызова инструмента → `isError`. Сервер не должен умирать из-за одной странной страницы.

## 6. SDK вместо ручного протокола

Ручной протокол полезен, чтобы понять механику, и когда важны ноль зависимостей и один бинарник. В остальных случаях бери официальный SDK: он сам делает схемы из типов, валидацию, новые версии протокола, другие транспорты (HTTP).

### Python (FastMCP, из официального пакета `mcp`)

```python
# pip install "mcp[cli]"
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("mini")

@mcp.tool()
def shout(text: str) -> str:
    """Переводит текст в верхний регистр. Используй, когда пользователь просит «прокричать» фразу."""
    return text.upper() + "!!!"

if __name__ == "__main__":
    mcp.run()   # stdio
```

Схема аргументов берётся из аннотаций типов, описание — из docstring.

### Другие

- TypeScript: `@modelcontextprotocol/sdk`
- Go: `github.com/modelcontextprotocol/go-sdk`
- Документация и спецификация: <https://modelcontextprotocol.io>

## 7. Если у сервиса нет API

Метод, которым сделан этот проект (подробно — [ARCHITECTURE.md, раздел 9](ARCHITECTURE.md#9-как-мы-исследовали-сайт)):

1. Поискать официальный API и проверить, включён ли он.
2. Разобраться с авторизацией. Для личного инструмента проще и безопаснее всего работать с сессией, которую пользователь сам открыл в браузере, чем хранить пароль и проходить второй фактор за него.
3. DevTools → Network: какие JSON-запросы делает сам сайт. Часто там есть внутренний API.
4. То, чего нет в JSON, — парсить HTML по устойчивым маркерам (`data-*`, `role`, `id`).
5. Формы — повторить руками с открытым Network, выписать все поля и порядок запросов.
6. Изменяющие действия — сначала `dry_run`, проверка на живом сайте, потом боевой режим.

Уважай правила сервиса и нагрузку: кэшируй, не делай сотни запросов в цикле, работай только со своим аккаунтом.

## 8. Распространение

- **Один бинарник** без зависимостей (Go, `CGO_ENABLED=0`) — пользователю ничего не нужно ставить.
- **GitHub Releases** + стабильный URL `releases/latest/download/<файл>`.
- **Скрипт установки**: определить ОС/архитектуру → скачать → прописать в конфиг клиента (с бэкапом) → интерактивная настройка. При `curl … | sh` stdin занят — интерактив читать из `/dev/tty`.
- **Секреты** — в конфиг-папке пользователя с правами `0600` или в системной связке ключей, никогда в репозитории и в `claude_desktop_config.json` в открытом виде, если можно иначе.
- Для Claude Desktop есть ещё формат **Desktop Extensions** (`.mcpb`, ранее `.dxt`) — архив с манифестом, ставится двойным кликом. Удобно для нетехнических пользователей.

## 9. Чеклист перед релизом

- [ ] stdout — только протокол, логи в stderr
- [ ] notification без ответа, request всегда с ответом с тем же `id`
- [ ] ошибки инструментов через `isError` с понятным текстом «что делать»
- [ ] описания инструментов говорят, откуда брать аргументы и что вернётся
- [ ] ответы компактные, размер ограничен
- [ ] изменяющие действия помечены, безопасный режим по умолчанию, есть `dry_run`
- [ ] все запросы только к нужному хосту; пути файлов санитизированы
- [ ] секреты с правами `0600`, не в репозитории
- [ ] протестировано: pipe, Inspector, живой клиент
- [ ] README: установка в одну команду, где взять креды, что делать при типичных ошибках

## 10. Для собеседования

**«Что такое MCP?»** — открытый протокол подключения LLM-приложений к внешним инструментам и данным. JSON-RPC 2.0 поверх stdio или HTTP; сервер объявляет tools/resources/prompts, клиент (Claude Desktop, IDE) передаёт их модели, модель решает, что вызвать.

**«Как устроен твой сервер?»** — Go, без зависимостей. Транспорт — цикл по stdin с горутиной на запрос и мьютексом на запись. Moodle без официального API: сессия из браузера (cookie + CSRF `sesskey`), внутренние AJAX-функции веб-интерфейса там, где они открыты, HTML-парсинг форм и страниц для остального. Сдача файлов повторяет цепочку браузера: форма → draft area → `repository_ajax upload` → сохранение формы.

**Что отличает хороший ответ от отличного:**

| тема | хорошо | отлично |
|---|---|---|
| протокол | «JSON-RPC по stdio» | + notification vs request, два уровня ошибок, почему stdout нельзя трогать |
| дизайн tools | «сделал 8 функций» | + гранулярность по задачам пользователя, описания как промпт, next-step ссылки в ответах |
| надёжность | «работает» | + dry_run, destructiveHint, recover, WaitGroup на EOF, фикстурные тесты парсеров |
| безопасность | «храню токен» | + 0600, привязка к хосту, санитизация путей, не храню пароль и не обхожу 2FA |
| реверс сайта | «спарсил HTML» | + метод: официальный API → Network → перебор AJAX → устойчивые маркеры → dry-run |

**Вопросы, которые могут задать:**

- *Почему не SDK?* — один статический бинарник под 6 платформ, ноль зависимостей, протокол для tools-only тривиален; для продакшн-сервера с HTTP-транспортом взял бы SDK.
- *Что будет, если Moodle обновят?* — AJAX-функции стабильны; HTML-парсинг хрупок → фикстурные тесты ловят поломку, маркеры семантические (`data-region`), а не позиционные.
- *Как масштабировать на многих пользователей?* — stdio-сервер локален и однопользовательский по природе; для общего сервиса — HTTP-транспорт, OAuth, хранение сессий на сервере, rate limiting.
